このシステムは「Web 管理画面」「スマホアプリ」「サーバー(API と定期処理)」でできています。本番では、次のサービスを組み合わせて動かします。

2. 進める順番とスケジュールの目安

審査や番号の発行に日数がかかるものがあるので、時間のかかるものから先に申し込むのがこつです。

順やることかかる日数の目安ポイント
1D-U-N-S 番号の取得(会社の国際的な ID)数日〜数週間Apple・Google に「組織」として登録するのに必要。最初に申し込む
2独自ドメインの取得即日メール送信の設定にも使う
3Azure の契約即日〜数日請求書払いにする場合は与信審査あり
4Stripe の申し込み数日〜2週間事業内容・特定商取引法の表記の審査あり
5Apple Developer Program(組織)数日〜2週間D-U-N-S 番号が必要。電話確認が来ることがある
6Google Play Console(組織)数日〜2週間D-U-N-S 番号と本人確認が必要
7Expo・Firebase のアカウント即日無料で作れる
8開発側で本番環境を組み立て・試験1〜3週間1〜7 の情報がそろってから
9アプリの審査数日〜数週間差し戻しがあると延びる
おすすめ: 1〜7 の申し込みを同じ週にまとめて行うと、全体で 1〜2 か月程度で公開できる見込みです(審査の結果しだいで前後します)。

3. 会社として先に用意するもの

3-1. D-U-N-S 番号 必須

何か: 会社ごとに付く世界共通の 9 桁の番号です。Apple と Google が「本当にある会社か」を確かめるのに使います。

  1. Apple の「D-U-N-S Number 検索」ページ(Apple Developer のサイト内)で、自社がすでに登録されていないか調べる
  2. 無ければ、同じページから無料で申請する(日本では東京商工リサーチが発行)
  3. 番号が届いたら控えておく。会社名・住所は登記と同じ英語表記にそろえる(違うと Apple の審査で止まる)

3-2. 独自ドメイン 必須

何か: サービスの住所です。例として、Web 管理画面を app.example.co.jp、メールの送り主を no-reply@mail.example.co.jp にします。

  • 会社のドメイン(example.co.jp など)をすでに持っていれば、その「サブドメイン」を使うのが簡単です
  • DNS(住所録)の設定を変えられる人を社内で決めておいてください。メール送信とサーバーの設定で、DNS にいくつか記録を足す作業が出ます(手順は各章で案内します)

3-3. 会社の窓口・メールアドレス

  • 各サービスの登録には、個人ではなく会社の共有メールアドレス(例: dev-admin@example.co.jp)を使ってください。担当者が替わってもログインできなくなりません
  • 各サービスで2 段階認証を必ず有効にし、認証アプリは担当者 2 名以上で持つか、予備コードを金庫に保管してください
  • カード払いのサービスが多いので、法人カードを 1 枚用意しておくと手続きが進みます

4. Microsoft Azure(サーバー・データベース・保管庫) 必須

何のために: API・Web 管理画面・定期処理(期限アラート・月次の確定・データの自動削除)を動かし、データを保管します。

4-1. 契約の手順

  1. azure.microsoft.com で会社の共有メールアドレスから Microsoft アカウントを作り、「従量課金(Pay-As-You-Go)」で申し込む(法人カードが必要)
  2. 請求書払いにしたい場合は、Microsoft のパートナー(販売代理店)経由の契約(CSP)も選べます。日本円・請求書で払えます
  3. Azure ポータル(portal.azure.com)で 予算アラート を設定する(例: 月 3 万円を超えたらメール)。使いすぎを防げます
  4. 開発側の担当者を「ユーザー」として招待し、作業に必要な権限(後述)を付ける

4-2. 作るもの一覧(開発側で作成も可能)

次の部品を「東日本(Japan East)」に作ります。開発側に権限をいただければ、こちらで作成・設定できます。

部品(Azure での名前)用途設定のポイント
リソースグループ部品をまとめるフォルダー例: zairyu-prod。試験用に zairyu-stg も別に作ると安全
App Service(Linux)API と Web 管理画面を動かすNode.js 22 以上。最初は小さめのプラン(B1〜P0v3 程度)。「常時接続」をオン。HTTPS のみ

ストレージ アカウント(Blob)カードの写真の保管コンテナーは「非公開」。匿名アクセスを無効。論理削除(誤削除の取り消し)を 7 日程度

4-3. 権限の考え方(「誰が何をできるか」)

  • サーバー(App Service と定期処理)には「マネージド ID」(パスワードの要らない Azure 内の身分証)を付け、次の 2 つだけを許可します
    • Key Vault: 「Key Vault Crypto User」(鍵で包む・開ける)と「Key Vault Secrets User」(秘密を読む)
    • ストレージ: 「Storage Blob Data Contributor」(写真の保存・取り出し)
  • 人の権限は最小限に。普段の運用担当は「閲覧者」、設定変更をする人だけ「共同作成者」にします
  • データベースのユーザーは、プログラムが最初の起動時(マイグレーション)に役割ごとに作ります(アプリ用・運営者用・削除処理用など)。管理者パスワードは Key Vault に保管します

4-4. サーバーに設定する値(開発側で設定)

設定の名前中身
DATABASE_URLデータベースの接続先(パスワード入り。Key Vault に保管して参照)
AUTH_JWT_SECRET / AUTH_SECRET_BOX_KEYログインの合鍵・認証アプリの鍵を守る鍵(ランダムに作って Key Vault に保管)
VAULT_KEY_PROVIDER=azure / AZURE_KEY_VAULT_KEY_ID暗号の親鍵として Key Vault の鍵を使う
BLOB_STORE=azure / AZURE_STORAGE_ACCOUNT_URL / AZURE_STORAGE_CONTAINER写真の保管先
ACS_CONNECTION_STRING / ACS_SENDER_ADDRESSメール送信(5 章)
NOTIFY_PUSH=expoプッシュ通知を Expo 経由で送る(7 章)
SECURE_COOKIES=true / NODE_ENV=production本番用の安全設定
大事: これらの値(特にパスワード・鍵・接続文字列)は、メール・チャット・スクリーンショットで送らないでください。Key Vault に入れるか、Azure の管理画面で開発側に権限を付けていただければ、こちらで設定します(12 章)。

5. メール送信(Azure Communication Services) 必須

何のために: パスワード再設定、期限が近いカードのアラート、偽造の疑いの通知、未払いのお知らせなどを、顧客企業の担当者へメールで送ります。

  1. Azure ポータルで「Email Communication Services」を作る(データの場所は「Japan」)
  2. 「ドメインを追加」→「カスタム ドメイン」で mail.example.co.jp を登録する
  3. 画面に出る TXT・SPF・DKIM(2 つ) の記録を、自社の DNS に足す(DNS の担当者の作業。コピーして貼るだけ)
  4. Azure の画面で「確認」を押し、すべて「確認済み」になるまで待つ(数分〜1 日)
  5. 送り主のアドレス(例: no-reply@mail.example.co.jp)と表示名(例: 在留カード管理)を決める
  6. 「Communication Services」を作り、上のメールのドメインを「接続」する。接続文字列は Key Vault に保管
迷惑メールに入らないために: SPF・DKIM に加えて DMARC(_dmarc の TXT 記録)も設定してください。最初は送れる通数に上限があるので、顧客が増えたら Azure に上限の引き上げを申請します。

費用: 送った通数と容量に応じた従量課金で、月数百〜数千通なら数百円程度の見込みです(要確認)。

6. 決済(Stripe) 必須(手動請求で始める場合は後でよい)

何のために: 顧客企業から月額料金をカードで自動的に集金し、請求書・領収書を出します。料金は「基本料+登録人数×単価(段階制も可)」で、運営者コンソールのプランで決めています。

6-1. 申し込み

  1. stripe.com/jp で会社として申し込む(代表者の本人確認書類・登記の情報・入金先の銀行口座が必要)
  2. 事業内容は「法人向けの在留カード管理クラウドサービス(月額課金)」のように具体的に書く
  3. Web サイトに特定商取引法に基づく表記・利用規約・プライバシーポリシー・料金の説明を載せておく(審査で見られます。11 章)
  4. 審査が終わるまでは「テストモード」で開発側が試験できます

6-2. 設定

  • 使う機能: Stripe Billing(定期課金)と Customer Portal(顧客がカードの変更・請求書の取得を自分で行う画面)
  • 請求書払い(銀行振込)を希望する顧客がいる場合は、Stripe の「請求書」機能の振込も使えます
  • Webhook(Stripe から「支払いが成功した・失敗した」を知らせてもらう仕組み)の受け口を開発側で作り、Stripe に登録します
  • 開発側に渡すもの: 本番・テストのシークレットキーとWebhook の署名シークレット(どちらも Key Vault へ。チャットに貼らない)
アプリ内で課金しない理由: スマホアプリに料金の表示や購入の画面を置くと、Apple・Google の手数料の対象になり審査も厳しくなります。このサービスは契約と支払いを Web だけで行い、アプリは法人の社員だけが使う形にしています(App Store の規約 3.1.3(c) の考え方)。

費用: 初期費用・月額は無し。日本のカード決済で 1 件あたり 3.6% 程度の手数料(執筆時点の目安。要確認)。

現状: 料金の計算・未払い時の制限・運営者コンソールでの契約状態の変更は実装済みです。Stripe との接続(顧客の作成・定期課金・Webhook)は、契約後に開発側で実装します(13 章)。

7. プッシュ通知(Expo・Firebase・Apple) 必須

何のために: 「期限が近いカードがあります」「偽造の疑いがあります」などを、担当者のスマホにすぐ知らせます。通知の文面には氏名やカード番号を入れていません。

7-1. Expo(EAS)

  1. expo.dev で組織(Organization)のアカウントを作り、開発側を招待する
  2. アプリの「プロジェクト」を作る(開発側で可能)。アプリの組み立て(ビルド)とストアへの提出もここから行います
  3. 無料プランで始められます。ビルドの回数が多くなったら有料プランを検討します

7-2. Firebase(Android の通知)

  1. console.firebase.google.com でプロジェクトを作る(Google アナリティクスは「無効」で可)
  2. Android アプリを追加し、パッケージ名にアプリの ID(本番用に決める。例: jp.co.example.zairyu)を入れる
  3. 「サービス アカウント」の鍵(JSON ファイル)を作り、Expo の管理画面にアップロードする(開発側で実施可能。ファイルはメールで送らない)

7-3. Apple(iPhone の通知)

8 章の Apple Developer Program の登録後に、「APNs キー」を作って Expo に登録します(開発側で実施可能)。

8. Apple(iPhone アプリ)と App Store 必須(iPhone 対応時)

8-1. Apple Developer Program(組織として登録)

  1. D-U-N-S 番号を用意する(3 章)
  2. developer.apple.com/programs から「組織」として申し込む。申し込む人は会社を代表して契約できる立場の人(またはその委任を受けた人)
  3. Apple から電話や書類の確認が来たら対応する
  4. 年会費を払う(執筆時点で年 12,980 円程度・要確認)
  5. 開発側を「App Store Connect」のユーザーとして招待する(役割: 「App Manager」または「Developer」)

8-2. このアプリならではの注意

  • NFC(在留カードの IC の読み取り): iPhone でカードの IC を読むには、Apple の「NFC Tag Reading」の機能を有効にします(開発側で設定済みの項目あり)。iPhone 7 以降で使えます
  • 審査で聞かれやすい点(審査メモに書きます)
    • 法人の社員だけが使うアプリで、個人は登録できないこと。契約と支払いは Web で行うこと
    • 審査用のデモアカウント(テスト用の会社・ダミーの登録者)を用意すること
    • カードの写真は端末の中だけで読み取り、外部の AI に送らないこと。カメラロールに保存しないこと
  • iPhone では、開発側でまだ実機の確認をしていません(13 章)。審査の前に iPhone での試験期間をとってください
社内だけで配る方法: 一般公開せずに特定の顧客だけに配るなら、「Apple Business Manager」の「カスタム App」という配り方もあります。顧客企業が Apple Business Manager に登録している必要があります。

9. Google Play(Android アプリ) 必須

  1. play.google.com/console で「組織」としてデベロッパー アカウントを作る(D-U-N-S 番号・会社の連絡先・本人確認が必要)
  2. 登録料を払う(執筆時点で 25 米ドル・1 回だけ・要確認)
  3. 開発側をユーザーとして招待する(権限: アプリの作成・リリース)
  4. アプリを作り、次の情報を入力する(開発側で下書きを用意できます)
    • ストアの説明文・スクリーンショット(個人情報の写っていないダミーで作ります)
    • データ セーフティ(どんなデータを集め、どう守るか): 氏名・住所・在留カードの情報・写真を、法人の業務のために集め、暗号化して保管し、第三者と共有しないこと
    • プライバシーポリシーの URL
    • 審査用のデモアカウント
  5. 最初は「内部テスト」→「クローズド テスト」で試し、問題がなければ「製品版」に出す
新しい個人開発者のアカウントの場合の注意: Google Play では、個人アカウントは公開前に一定人数・一定期間のテストを求められます。組織アカウントで登録すると、この条件を避けやすくなります。
社内配布だけでよい場合: 「Managed Google Play」を使って、顧客企業の端末だけに非公開で配る方法もあります。

10. エラー監視(Sentry など) 任意

何のために: 本番で起きたエラーをすぐに開発側に知らせ、原因を調べやすくします。

  • Azure の Application Insights でも基本的な見張りはできます。より詳しく見たい場合に Sentry を足します
  • sentry.io で組織を作り、開発側を招待する。データの保存場所(リージョン)を選べる場合は確認する
  • 個人情報を送らない設定が必須です(氏名・カード番号・住所・写真を送らない)。開発側で、送る前に個人情報を消す設定を入れてから有効にします
  • 無料プランで始められます(送る量が増えたら有料)

11. 法務・書類の準備 必須
